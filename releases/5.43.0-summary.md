# Warlock.js 5.43.0 — release summary

Released 2026-11-01.

All **33 packages** (`@warlock.js/*` and `create-warlock`) move to 5.43.0 together;
keep every family package on the same version. This release adds sliding cache expiry,
idempotent runs, probabilistic cache structures, job timeouts, and three ways to cut AI
model calls. One interface change affects custom cache drivers (see below).

---

## 1. Breaking changes

- **Custom cache drivers that implement `CacheDriver` directly** must add
  `extend(key, ttl): Promise<boolean>` (return `false` for a missing key). Drivers that
  extend `BaseCacheDriver` inherit a working default and need no change.

---

## 2. Cache (`cache`)

- **`cache.extend(key, ttl)`** keeps a value and resets its expiry to `ttl` from now (a
  sliding expiry: "the user is active, keep the session another 30 minutes"). It does not
  add `ttl` to the time left, and it returns `false` for a missing or expired key. Every
  driver implements it (Redis `PEXPIRE`, Postgres `UPDATE`, in place on the memory drivers),
  and namespaces and tagged caches forward it.
- **`idempotent(key, fn, { ttl })`**, also `cache.idempotent(...)`: concurrent calls with one
  key share a single run, and repeat calls within `ttl` return the stored result (the
  Idempotency-Key pattern for payments, webhooks and retried jobs). `ttl: 0` only shares
  calls in flight and never touches the store. A failed run is never stored.
  `distributed: true` uses the cache lock so servers sharing a driver run `fn` once.
- **`cache.structures`**: `bloom` ("definitely not" / "probably yes"), `cuckoo` (membership
  with removal), `uniqueCounter` (HyperLogLog, about 12 KB per counter, with
  `uniqueCounter.merge(keys)`) and `frequency` (Count-Min estimates plus Top-K). They run on
  Redis (RedisBloom when the server has it, plain Redis otherwise) and on the `memory`,
  `memoryExtended` and `lru` drivers. Other drivers throw `CacheUnsupportedError`.

---

## 3. Job timeouts (`queue`)

- `defineJob({ timeout: "2m", failOnTimeout?: boolean })`, also per dispatch and in
  `queue.defaultJobOptions` (dispatch > `defineJob` > defaults). An attempt that outlives its
  limit fails with `JobTimeoutError`, and normal `attempts` and `backoff` apply;
  `failOnTimeout: true` fails the job without retrying. BullMQ, `local` and `memory` behave
  the same.
- Handlers receive `ctx.signal`, which aborts on timeout. Pass it to `fetch` and database
  calls: a handler that ignores it keeps running in the background after the attempt fails.

---

## 4. Fewer AI model calls (`ai`)

- **`ai.semanticRouter()`** plugs into `ai.supervisor({ router })`. It routes by embedding
  similarity to example phrases per intent and sends only unsure messages to a fallback,
  usually `ai.router({ model, intents })`. Example vectors are embedded once and stored in
  memory or any cache driver (Redis, pg); reports carry `routedBy`, the score and the
  runner-up. `learn: true` adds confident fallback decisions as examples, capped per intent.
- **`memoize`** on a read-only tool reuses the result of an identical call within a run or a
  session. Errors are never kept.
- **`ai.middleware.dedupe()`** makes identical model calls in flight at the same moment share
  one provider call. Streaming runs are not deduplicated.

---

## 5. Upgrade notes

1. **Update the family.** Run `npx warlock update`.
2. **Read what changed.** Run `npx warlock release-notes --from 5.42.0`.
3. **Custom cache driver?** If it implements `CacheDriver` without extending
   `BaseCacheDriver`, add `extend(key, ttl)`.
4. **Long-running jobs?** Add a `timeout` and pass `ctx.signal` to network and database calls.
