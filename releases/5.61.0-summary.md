# Warlock.js 5.61.0 — release summary

Released 2026-11-20.

All **34 packages** (`@warlock.js/*` and `create-warlock`) move to 5.61.0 together;
keep every family package on the same version. This minor gives devtools a richer Jobs tab
(scheduler run history and queue counts), makes closed production monitor URLs answer like
any unknown URL, and makes the Grimoire dev tab read route facts from the running dev
server. The packages with changes are `core`, `devtools`, `grimoire`, `queue` and `scheduler`.

## Check first

Nothing needs action before upgrading. Everything below is additive.

---

## 1. What changed most

- **The Jobs tab shows what ran.** Each schedule lists its last duration, last error, runs,
  failures and recent runs (error messages scrubbed like request errors); each queue shows
  waiting, active, delayed, failed and completed counts. A queue driver that does not implement `counts()` shows "Counts not available".
- **Scheduler run history.** Every job keeps its last 20 runs in memory (start, duration,
  success, failed or skipped, error message) and totals in `job.stats`.
- **Closed monitor URLs look like any unknown URL.** When the production monitor refuses a
  request (no session, disabled, address not allowed, tab off), the answer now comes from the
  app route that would answer that URL (a web site's catch-all), so a web site's `route_not_found`
  page or JSON is returned instead of Fastify's default 404, with the same rate-limit headers and
  the same 429 as any unknown URL.
- **The Grimoire dev tab opens with fresh routes, and quickly once warmed.** Routes, events and
  jobs come from the running dev server, so the first open shows fresh routes without
  `warlock grimoire build` and without a second boot of the app. The book is warmed in the
  background when the dev server starts: on a 10,400-file app, the first open after the warm-up
  takes about 0.1 s instead of about 6.6 s. An open that comes before the warm-up ends still
  waits for it (about 6.7 s on that app). Streaming partial answers is not part of this release.

## 2. New options and APIs

- **Scheduler.** `job.history`, `job.stats`, `job.keepHistory(n)`, `Job.defaultHistorySize`.
- **Queue.** Optional `QueueDriver.counts(queue)`, `QueueCounts`, `queueCounts(queue)`,
  `currentQueueDriver()`.
- **Core.** `answerUnknownUrl(request, reply)` on the router; `startLiveEventRecording()` and
  `liveInspectOptions()` on `@warlock.js/core/tooling`.
- **Grimoire.** `createWarlockAdapter({ live: true })`, `liveInspect()`, snapshot source option
  `liveFacts`; check `GR5010` (warning); flows with no writes may skip the `duplicate` and
  `double submit` case questions (`GR1012`).
- **Devtools.** The Queries tab works when production is enabled only through
  `devtoolsConnector({ production })`.

## 3. Upgrade notes

- A custom queue driver keeps working; implement `counts(queue)` to get counts in the Jobs tab.
- `GR5010` is a warning, so a `grimoire check` that passed still passes; it may list backticked
  names in "Changes with" that are not declared conditions.

## 4. Verified

- One typecheck of the family, the strictness gate and every package's full test suite ran green on the final tree,
  along with format, lint, the public-text, skill and release-note checks, the devtools UI gate and the docs build.
- Queue counts from the BullMQ driver ran against a live Redis 7 with jobs in every state; `driver.counts()` and
  `queueCounts()` matched.
- The Grimoire first-open timings were measured on a generated 10,400-file app, three runs each, median reported.
- Closed monitor URLs were compared with an unknown URL of an app with a web catch-all and of a plain core app, in
  JSON and HTML, with rate limiting on. `GET` and `HEAD` answers match exactly; a closed URL hit with a request body
  can still differ, as the devtools security page explains.
