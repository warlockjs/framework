# Warlock.js 5.56.0 — release summary

Released 2026-11-17.

All **34 packages** (`@warlock.js/*` and `create-warlock`) move to 5.56.0 together;
keep every family package on the same version. This minor adds a production monitor to
`@warlock.js/devtools`: the dashboard can now run in a live app at a path you choose,
behind its own accounts and two-factor sign-in. It is off by default. The dashboard is
also rebuilt with React. The packages with changes are `devtools`, `core` and
`grimoire`. Nothing changes for an app that does not turn the production monitor on,
apart from the dashboard rebuild and the notes under "Upgrade notes".

## Check first

- **The production monitor is opt-in.** Until you set `production.enabled`, nothing is
  mounted, nothing is captured and no table is read. See section 4 for the steps to turn
  it on.
- **The dashboard is a React app now.** It replaces the old plain JavaScript files in
  `ui/app.js`. Panel view modules keep working unchanged. A view that used the old
  dashboard's CSS classes may look different.
- **New reserved panel ids.** `resources`, `health`, `errors`, `jobs`, `instances`,
  `auth`, `account` and `admin` belong to devtools. A panel that uses one is left out,
  with a message.
- **`GET <path>` without a trailing slash now redirects to `<path>/`**, in development
  too.
- **`GET api/logs` rows now carry `instance` and `requestId`.**

---

## 1. What changed most

- **Production monitor (`devtools`).** The dashboard runs in production at a path you
  set with `DEVTOOLS_PATH`. To anyone who is not signed in, every URL under it answers
  the app's own 404, so the path is not given away.
  - **Accounts.** Admin and viewer roles, stored in your database through Cascade
    (MongoDB or SQL). Invite links, a forced password change at the first sign-in, and
    a user list for admins.
  - **Two-factor sign-in.** Authenticator app (TOTP) and passkeys, plus 10 single-use
    recovery codes. Admins need a second factor by default (`twoFactor: "admins"`).
  - **Protection.** Sign-in rate limits per account, per IP and overall, with a lockout;
    a CSRF header on every write; HTTPS only by default; an optional IP allow list; and
    an audit log.
  - **Disable switch.** An admin can close the dashboard from the dashboard. Every
    instance reads the switch within 5 seconds and it survives restarts.
    `warlock devtools:enable` opens it again.
- **Production panels.** Requests (sampled), Queries and Routes with latency
  statistics, Resources, Health, Errors, Logs and Jobs. Queries and Routes show their
  statistics in development too.
- **EXPLAIN by query shape.** Admins can explain a query shape from the Queries tab.
  Plans do not run the query unless you allow it.
- **Several instances in one view.** Each process writes a report every 10 seconds and
  the dashboard merges them. An instance picker selects all instances or one process.
- **Dashboard rebuilt with React (`devtools`).** The same tabs with the same features.
  The panel API is the same, so package panels keep working.
- **Grimoire tab in production (`grimoire`).** It is read-only there: it opens the book
  and writes no file.
- **Request log exclusion and TOTP helpers (`core`).** See section 3.

## 2. The production monitor in more detail

- **Start-up checks.** When the monitor is enabled but cannot start safely, the app
  refuses to boot with a `DevtoolsProductionConfigError` (`DT001` to `DT010`). It needs
  a path, a first admin (`DEVTOOLS_ADMIN_EMAIL` with either `DEVTOOLS_ADMIN_PASSWORD`
  or `DEVTOOLS_SETUP_TOKEN`, not both), `encryption.key` in `src/config/encryption.ts`,
  a database connection and the migrated tables.
- **Path.** It starts with `/`, has at least 8 characters and uses only letters,
  digits and `- _ . ~ /`. The boot log shows only its first characters. Core's request
  log and the one-line request summary skip it.
- **Sign-in limits.** The window is 15 minutes. An account is refused after 5 failures
  and an IP after 20. After 100 failures in total the whole dashboard answers 404 for 15
  minutes. A correct password does not reset the failed-try count; only a completed
  sign-in does. An IPv6 client counts by its /64. A caller over the IP limit costs no
  password check.
- **Account changes.** Adding or removing an authenticator app or a passkey asks for the
  current password. Removing also accepts a passkey check from the last 5 minutes, which
  works once. New recovery codes need a code from the authenticator app or a passkey.
- **Sessions.** Signed out after 30 idle minutes or 8 hours (`session.idleMinutes`,
  `session.maxHours`). Invite links last 24 hours, work once and keep their token after
  the `#`, so it never reaches a server log. The last admin cannot be removed or demoted.
- **Recovery.** `warlock devtools:reset-admin --email <email>` creates or resets an
  admin, prints a temporary password, removes its second factors and signs it out
  everywhere. `warlock devtools:enable` also clears a global lock and the failure
  counts.
- **What is captured.** One random draw per request decides whether it is sampled
  (`sampleRate`, 0.1). A sampled request is captured fully and stored for
  `requestRetentionHours` (24). A request that is not sampled does no capture work; if it
  is slow (`slowRequestMs`, 1000) or fails, it is kept as a summary without a timeline.
  Memory is bounded per process: 200 sampled requests, 200 queries per request, 500
  query shapes, 300 routes and 100 error groups. Each process writes at most 120 samples
  a minute.
- **What is removed.** Nothing that leaves the process carries a value. Queries are kept
  as shapes (placeholders, no literals or bindings). Headers, bodies, query strings,
  params, log `context` and cache keys are not kept. Quoted values, emails and `{ … }`
  documents are removed from request errors and from `error` log lines before they are
  grouped, stored or shown. The request path is kept as the app served it, so keep
  secrets out of URL paths.
- **EXPLAIN.** PostgreSQL runs plain `EXPLAIN (FORMAT JSON)` for one `SELECT` or `WITH`
  statement that writes nothing, inside a read-only transaction that is rolled back.
  MongoDB uses `queryPlanner` for `find`, `aggregate` and `count`; an aggregate with
  `$out` or `$merge` is never explained. Plans that run the query (PostgreSQL
  `EXPLAIN ANALYZE`, MongoDB `executionStats`) run only with `explain.executing: true`.
  Production plans show `?` in place of the query's values. Only the process that ran
  the query can explain it. Every run is audited.
- **Tabs in production.** Requests, Queries, Routes, Resources, Health, Errors, Logs and
  Jobs are on. Mail, AI, Agents, API and Processes are off unless `panels` sets the id to
  `true`. A package panel is on when it declares `production: true`. `panels: { mail:
  false }` turns any tab off. The API tab builds its OpenAPI document from the registered
  routes, so under `warlock start` response resources are named `Resource1`,
  `Resource2` and so on.
- **Behind a proxy.** A forwarded header is read only when the socket peer is listed in
  `trustedProxies` (addresses, CIDR ranges, `"loopback"` or `"private"`). Set `origin` to
  your public origin so the CSRF check and passkeys never depend on a header.
- **Not available yet.**
  - The scheduler keeps no run history. The Jobs tab shows each scheduled job with its
    schedule, last run and next run; duration, last error and failure counts are empty.
  - Queue job counts appear only when the queue driver reports them. Today the tab says
    they are not available.
  - The live stream is per instance: it follows the process that served your connection.
  - On MongoDB, the Queries tab needs command monitoring. Core turns `queryEvents` on
    for a process that serves HTTP when `devtools.production.enabled` is `true` in
    `src/config/devtools.ts`; an explicit `queryEvents` on the data source wins.

## 3. New options and APIs

- **`devtools`, enabling:** `production.enabled` in `src/config/devtools.ts`. Environment:
  `DEVTOOLS_PATH`, `DEVTOOLS_ADMIN_EMAIL`, `DEVTOOLS_ADMIN_PASSWORD`,
  `DEVTOOLS_SETUP_TOKEN` (at least 32 characters).
- **`devtools`, exports from `@warlock.js/devtools/production`:** `devtoolsMigrations`
  and `registerDevtoolsCommands()`, which adds `warlock devtools:enable` and
  `warlock devtools:reset-admin`.
- **`devtools`, options under `devtools.production`** (defaults in brackets):
  `path` (`DEVTOOLS_PATH`), `sampleRate` (0.1), `slowRequestMs` (1000), `slowQueryMs`
  (200), `maxRequests` (200), `requestRetentionHours` (24), `maxStoredSamplesPerMinute`
  (120), `reportIntervalMs` (10000), `trustedProxies` (`[]`), `requireHttps` (`true`),
  `allowedIps` (`[]`), `origin`, `session.idleMinutes` (30), `session.maxHours` (8),
  `twoFactor` (`"admins"` or `"everyone"`), `rateLimits.windowMinutes` (15),
  `rateLimits.account` (5), `rateLimits.ip` (20), `rateLimits.global` (100),
  `rateLimits.lockMinutes` (15), `explain.executing` (`false`), `panels`, `logLevels`
  (`["warn", "error"]`), `auditRetentionDays` (90), `passkeys.rpName` and
  `passkeys.rpId`. An invalid value stops the boot with `DT007`, naming the option.
- **`devtools`, storage:** seven tables or collections: `devtools_accounts`,
  `devtools_sessions`, `devtools_invites`, `devtools_audit`, `devtools_state`,
  `devtools_samples` and `devtools_reports`. No cache driver is needed.
- **`devtools`, panels:** a panel can set `production: true`, and its factory receives
  `mode` (`"development"` or `"production"`). In production a panel's GET routes need a
  signed-in user; every other method needs an admin and the CSRF header, and is written
  to the audit log.
- **`devtools`, live stream:** it sends `retry` and `hello` first, and request and log
  events carry `instance`.
- **`devtools`, other:** query shapes drop dollar-quoted strings. In development, a
  value logged as the message (such as an Error) shows as text, and a tab that fails to
  draw no longer blanks the dashboard. Error groups include log lines that carry a
  request id, and the Health tab records no error while the app boots. The server
  answers 503 with a build hint when `ui/dashboard/` is missing. The dashboard's
  Content-Security-Policy replaces the app's own, and an unknown asset under the
  dashboard path answers the app's own 404.
- **`core`:** `generateTotpSecret()`, `totpCode()`, `verifyTotp()` and `totpUri()` for
  authenticator-app codes. `excludeFromRequestLog(prefix)` keeps a URL prefix out of the
  persistent request log, and `isExcludedFromRequestLog(path)` tells whether a path is
  excluded. The one-line request summary (`http.log`) and the request lifecycle log skip
  excluded paths too. `onRequestEnd`'s `error` is now set for a 5xx that core answered
  after a middleware or handler threw.
- **`grimoire`:** `GrimoireDevtoolsPanel` gains `production`, and `GrimoirePanelContext`
  gains `mode`.

## 4. Upgrade notes

1. **Update the family.** Run `npx warlock update`, then
   `npx warlock release-notes --from 5.55.0`.
2. **Apps that do not enable the production monitor** change in four ways only: the
   dashboard is rebuilt in React, the reserved panel ids below, `GET <path>` redirects to
   `<path>/`, and `api/logs` rows gain two fields. Nothing is mounted or captured, and no
   table is needed.
3. **The old dashboard files are gone.** The plain JavaScript dashboard (`ui/app.js`) is
   replaced. Panel view modules keep working unchanged. If a view styled itself with
   the old dashboard's CSS classes, check how it looks.
4. **Reserved panel ids.** `resources`, `health`, `errors`, `jobs`, `instances`,
   `auth`, `account` and `admin`. A panel with one of these ids is left out with a
   message; rename it.
5. **The `production` panel flag.** A package panel shows in the production monitor only
   when it sets `production: true` (or the app sets its id to `true` in `panels`). Use the
   new `mode` argument of the panel factory to serve less in production. In production a panel's write
   routes need an admin and the CSRF header, and are audited.
6. **To turn on the production monitor:**
   1. Install `@warlock.js/devtools` as a regular dependency, not a development one.
   2. In `warlock.config.ts`, add `devtoolsConnector()` to `connectors`,
      `registerDevtoolsCommands()` to `cli.commands`, and `...devtoolsMigrations` to
      `database.migrations`.
   3. Set `production: { enabled: true, trustedProxies: [...] }` in
      `src/config/devtools.ts`.
   4. Run `npx warlock migrate`.
   5. Set `DEVTOOLS_PATH`, the first admin (`DEVTOOLS_ADMIN_EMAIL` with
      `DEVTOOLS_ADMIN_PASSWORD` or `DEVTOOLS_SETUP_TOKEN`) and `encryption.key`
      (64 hex characters).
   6. Sign in, change the password, add a second factor and save the recovery codes. You
      can then remove the password or token from the environment.

   Behind a TLS-terminating proxy, set `trustedProxies` and forward `X-Forwarded-For`,
   `X-Forwarded-Proto` and `X-Forwarded-Host`, or the dashboard answers 404. Turn proxy
   buffering off for the dashboard path so the live view updates at once. For passkeys,
   install `@simplewebauthn/server`; without it only the authenticator app is offered.

7. **MongoDB:** core turns `queryEvents` on for you when the monitor is enabled in
   `src/config/devtools.ts`. If you enable it only through options passed to
   `devtoolsConnector()`, set `queryEvents: true` on the data source yourself. It adds a
   small cost to every query.
8. **Documentation.** Read "Devtools in production" and "Devtools security" in the docs
   before you turn the monitor on.

## 5. Measured

Cost of the capture on 5.56.0, measured on an Intel Xeon Gold 6312U with Node 22. The
hooks were driven directly for 50,000 simulated requests with 3 phases, 5 queries and 1
log each (best of 3).

| Sample rate         | Added cost per request |
| ------------------- | ---------------------- |
| 0 (nothing sampled) | 0.13 µs                |
| 0.1 (the default)   | 1.32 µs                |
| 1 (every request)   | 12 µs                  |

On a real Fastify server (16 keep-alive clients on loopback, a handler of about 83 µs,
median of 3 runs), the default rate lowered throughput by 6 to 8 % in four runs, with
about ±3 % run-to-run noise, and a rate of 1 lowered it by 27 %. At a rate of 0 no loss
was measurable. That handler is much lighter than a real one: a handler that takes a few
milliseconds loses well under 1 % at the default rate. Measure your own app before
raising `sampleRate`.

The dashboard bundle is 123.6 KB gzipped (app.js 115.6 KB, app.css 8.0 KB).

We also ran the monitor in a small real app, built and started for production
(`warlock build` and `warlock start`) and in development, on MongoDB 6.0 and PostgreSQL
16, driven with curl, a Node script and headless Chromium:

- Every start-up refusal `DT001` to `DT010` stopped the boot as documented.
- Closed URLs (the dashboard path over plain HTTP, a wrong path, no session, a disabled
  dashboard) matched the app's own 404 in status, headers and body shape. The differences
  were the URL echoed in the default message and the length that follows from it.
- Sign-in, invite, roles, CSRF, disable, enable and `devtools:reset-admin` worked. Every
  data route answered real data, and every tab opened in Chromium.
- EXPLAIN gave plans on MongoDB and PostgreSQL, refused statements that write, and
  showed `?` in place of values.

The run found and fixed problems before release: an unknown asset under the dashboard
path answered a bare 404 instead of the app's, the API tab's frame was blocked by the
dashboard's `frame-ancestors` rule, and production plans carried the query's values.

Limits: one small app and one machine; the end-to-end run did not sign in with a passkey in a browser; and
the numbers above are for the capture hooks, not for every kind of app.
