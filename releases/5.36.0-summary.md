# Warlock.js 5.36.0 — release summary

Released 2026-10-21.

All **33 packages** (`@warlock.js/*` and `create-warlock`) move to 5.36.0 together;
keep every family package on the same version. Four changes are **breaking**
(see section 1); read them before upgrading.

---

## 1. Breaking changes

- **Vite 7 is no longer supported.** `@warlock.js/web` peers on `vite@^8.0.0` and
  `@vitejs/plugin-react@^6.0.0`. Plugin-react 6 requires Vite 8, so install both
  together. Vite 8 needs Node.js 20.19 or 22.12 and newer; Warlock already requires 22.15.
- **The test kit and the AI matchers need Vitest 5.** A runner that imports
  `VitestTestRunner` from `vitest/runners` fails on Vitest 5. Import `TestRunner` from
  `vitest` and call `this.onCleanupWorkerContext?.(cleanup)`, or let the codemod do it.
  The TypeScript types for `@warlock.js/ai`'s custom matchers (`toRouteTo`, `toConverge`,
  `toPassStep`, `toOutputShape`) also need Vitest 5. Runtime behavior is unchanged.
- **Pages embed only their own named API routes.** A browser call to a named route works
  only when the page's client code reaches that name. A name built at run time, or read
  from a module the build cannot follow, throws on that page. Declare it in the page
  setup's `config.apiRoutes`, or call the endpoint with an explicit `path` and `method`.
  Authorization is unchanged: a route in the table still answers `401` or `403` from its
  own guards. The server seam `resolveNamedApiRoutes(names)` returns an empty table when
  called without names; before, it returned every route.
- **Translation payloads carry only what the page uses.** A hydration payload no longer
  includes every translation group, in either translation mode. Apps that read the
  hydration payload directly, read keys built at run time without declaring them, or rely
  on every key being in the browser registry must update. Declare the keys with
  `config.translations`, or set `build: { translations: { prune: false } }` in the web
  connector options while you migrate.

### How to upgrade

- **Run the upgrade.** `npx warlock upgrade --from 5.35 --to 5.36.0`, with `--dry-run`
  first if you want to preview. Then run `npm install`, `npx warlock check` and
  `npx warlock build`. The upgrade skill has "5.35 to 5.36" sections for the route,
  translation and Vite/Vitest changes.
- **What the `vite-8-vitest-5` codemod rewrites.** It raises `vite` (8.3.3), `vitest` and
  `@vitest/*` (5.0.3), and `@vitejs/plugin-react` (6.1.2) in `dependencies`,
  `devDependencies`, `overrides` and `resolutions`, keeping each entry's `^`, `~` or exact
  style. It rewrites a generated `src/test-runner.ts` from `VitestTestRunner` to
  `TestRunner` from `vitest`.
- **What it lists for review, without editing.** Imports of the removed `vitest/coverage`,
  `vitest/reporters`, `vitest/environments`, `vitest/snapshot`, `vitest/suite`,
  `vitest/mocker` and `vitest/internal/module-runner` entry points; other names imported
  from `vitest/runners`; a top-level `esbuild` option in a Vite or Vitest config; and
  object-form `output.manualChunks`.
- **Page changes have no codemod.** `warlock check` reports `WL9019` for route calls it
  cannot read and `WL9104` for translation keys computed at run time. In production, read
  the `kind: "translations"` reports from `onClientError`.

## 2. Smaller, safer page payloads

- **Per-page API route table.** Each page embeds only the named API routes its client code
  reaches. The build finds them from string literals, template prefixes and the register
  hooks of setup files. `config.apiRoutes` covers names the build cannot see, and a
  `prefix.*` pattern covers every name under a prefix. Routes registered with
  `clientVisible: false` are never embedded, and a browser call to one is an error
  (`WL9020`). The hydration payload no longer repeats the table; its own script already
  carries it.
- **Why.** Before this release every page carried every named route, including guest pages.
  On one measured admin page the HTML was 56.7 KB, of which 22 KB was translations and
  6.5 KB the route table. Admin, auth and internal endpoints now appear only in pages that
  call them, so a visitor no longer receives the full API surface.
- **Shared translation groups.** The shared groups (default `app` and `common`) ship once
  per locale as a table whose URL carries its content hash. The document preloads it, and
  hydration waits for it. Production serves hashed tables with
  `Cache-Control: public, max-age=31536000, immutable`, and each locale's newest table at
  `/__warlock/translations/<locale>.json` with `no-cache`. Route-dictionary apps write the
  tables under `assets/translations/` at build time. Global-registry apps (`extend()` /
  `register()`) get them from the server at runtime. The server keeps the eight most recent
  tables per locale. Switching locale loads the other locale's table.
- **Per-page pruning, in both modes.** Every other group is pruned to the keys the page's
  client module graph can look up. Resolved statically: literal keys, template keys with a
  static prefix (which include their subtree), module-level constants, literal choices,
  `useTrans()` bindings under any local name, and `config.translations` declarations in the
  page's setup file. A key that cannot be resolved, such as `trans(key)` or a translator
  passed on as a value, makes that page fall back to every non-shared group.

  ```ts
  export const config = {
    apiRoutes: ["orders.*"],
    translations: ["statuses.*", "members.title"],
  };
  ```

- **Fixed per process (global registry).** Production builds copy the shared groups once,
  when the web connector boots. That copy and its hash stay fixed for the process, so every
  process of one build publishes the same table under the same name. Keys a page registers
  later travel inline in its payload.
- **Fallback order.** In the browser, a hashed table that answers 404 triggers a fetch of
  the unhashed latest table, then a retry of the hashed one. Only then does the browser
  report the failure and render keys. In development, a key the page reads but its payload
  lacks resolves from the full table, with one warning per key and page that names the
  declaration to add. In production, a missing key renders as its own text and is reported
  once through `onClientError`.
- **Translation options.** `build.translations` on the web connector sets `sharedGroups`
  (default `["app", "common"]`) and `prune` (default `true`). Development reads the same
  option. `prune: false` restores the previous per-page payload.
- **Inline payload budget.** `build.budgets.payload` sets the inline payload limit for each
  rendered document: default `64kb`, with route globs and a `warn` or `error` mode. The web
  runtime measures it and splits the hydration data and route table by section. An
  over-budget route is reported once per process with its largest keys. `warlock build`
  does not measure it. The browser end-to-end kit's `page.measurePayload({ limit })` records
  a document's inline payload as `payloads` evidence.

## 3. Vite 8, Vitest 5, plugin-react 6 and the docs site on Astro 7

- **Vite 8 on Rolldown.** The client build, the development server and the Warlock Vite
  plugins run on Vite 8 (Rolldown), with TypeScript transformed by Oxc. `warlock add web`
  declares `vite` `^8.3.3` and `@vitejs/plugin-react` `^6.1.2`.
- **Config moves.** Object-form `manualChunks` becomes
  `build.rolldownOptions.output.codeSplitting.groups`; `build.rollupOptions` still works
  but is deprecated. A top-level `esbuild: { jsx: "automatic" }` becomes
  `oxc: { jsx: { runtime: "automatic" } }`; `esbuild.target` is not converted. The
  development server's JSX runs through `oxc`, so the Vite deprecation warning is gone.
- **Decorators.** Vite 8 does not lower native decorators in the modules it transforms.
  Modules under `src/app` still load through Core. A decorated module under `src/web` needs
  `lowerStage3Decorators()` from `@warlock.js/core/vite` first in `plugins`, as the
  generated test config does.
- **Vitest 5.0.3 defaults that can change a green suite.** `clearMocks` is true; the `json`
  and `junit` reporters write to `.vitest/`; `-t` joins a test's names with `>`;
  `VITEST_POOL_ID` and `VITEST_WORKER_ID` start at 1; nested `vi.mock` and `vi.hoisted`
  calls throw; an unawaited `resolves` or `rejects` assertion fails the test. Vitest no
  longer searches parent directories for a config file, so run it from the package that
  owns the config. Review specs that rely on mock state surviving between tests.
- **Generators.** `warlock add test` generates a runner that extends `TestRunner` from
  `vitest` and declares `vitest` and `@vitest/coverage-v8` `^5.0.3`. The `create-warlock`
  template pins Vitest 5.0.3, and web projects declare Vite 8 and plugin-react 6. The
  generator's own dev dependencies use `@types/node` 22, the minimum Vitest 5 supports.
- **Docs site.** The docs site moves to Astro 7.3.6 with `@astrojs/mdx` 8.0.3 and Starlight
  0.42.5. Markdown tables render without the explicit `markdown.gfm` setting, which is removed;
  the docs table guard still checks every page.

## 4. Fixes

- **Development page edits.** Edits reach the browser without waiting for the sitemap
  subscription refresh. Under heavy machine load, an edit made right after deleting a layout
  or setup file could take longer than ten seconds to appear.
- **Cascade unset of a stored empty object.** `model.unset("field")` on a field holding `{}`
  is persisted. The model reports the change and `save()` issues the `$unset`. It was silently
  skipped, because an empty object has no leaves to diff.
- **E2E click and wait errors.** When `page.click()` (and `fill()` and `type()`, which click
  first) or a wait runs out of time, the error keeps the reason the target was last seen
  blocking. A CDP timeout caused by the shrinking deadline no longer replaces it, so the error
  reads, for example, "target is covered by DIALOG#modal".
- **Node builtins in `external`.** The client build's refusal of Node builtins in the bundler's
  `external` option works on Vite 8, where Rolldown no longer passes that option to
  `buildStart`. Without the fix, an externalized `fs` could ship unrefused.
- **Client budget attribution.** `clientBudgetModules` reads Rolldown's `renderedLength`, and
  a spec runs it on a real build.
