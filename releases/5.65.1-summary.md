# Warlock.js 5.65.1 — release summary

Released 2026-11-26.

All **34 packages** (`@warlock.js/*` and `create-warlock`) move to 5.65.1 together;
keep every family package on the same version. This patch stops an app-wide JSON error formatter from
replacing the replies the web client reads itself, so failed form actions show their errors again in apps
that use one. The package with changes is `core`.

## Check first

- If your app sets `http.errorResponse` and its formatter returns `undefined` for requests carrying the
  `x-warlock-data` header (the workaround for this bug), you can remove that branch.

---

## 1. What changed

- **Form action errors reach the page.** With an `http.errorResponse` formatter configured, a failed page
  action submitted from a `<Form>` answered 422 with the app's error envelope instead of `{ actionData }`,
  so `useActionData()` stayed empty and the client reported "status 422 without an actionData body". Core
  now leaves every reply to a request carrying `x-warlock-data` untouched: client navigations, `refresh()`
  and JavaScript form submits, including the data 404 for an unknown `_action` and loader errors on a
  client navigation. JSON API errors on the same server are still formatted, and submits without
  JavaScript were never affected.

## 2. Verified

- A core spec sends the same 422 and 404 JSON replies with and without the header: untouched with it,
  formatted without it, and an empty header value counts as no header.
- A web spec runs a real core HTTP server with an app formatter: a failing page action posted with
  `x-warlock-data: 1` answers 422 with `actionData.formErrors` in its body, the unknown-action data 404
  keeps `{ error: "not_found" }`, and an API route's 422 is still formatted. The web spec fails on 5.65.0.
- One typecheck of the family, the strictness gate and every package's full test suite ran green on the
  final tree, along with format, lint, the public-text, skill and release-note checks and the docs build.
