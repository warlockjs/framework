# Warlock.js 5.33.0 — release summary

Released 2026-10-19.

All **33 packages** (`@warlock.js/*` and `create-warlock`) move to 5.33.0 together;
keep every family package on the same version. **`@warlock.js/process` joins the
family** in this release.

This release makes **Oxlint + Oxfmt the only default toolchain**, adds MCP serving
request context and cancellation, live page data, app-scoped secrets, an AI panel
and input measurement, PM2 deployment commands, and owned process supervision.
It contains **breaking changes in a minor version** (Warlock.js does not follow
SemVer strictly). Read the upgrade steps and behaviour table before installing.

---

## 1. Read this first

### ESLint and Prettier are deprecated — migrate existing apps

ESLint and Prettier are **off by default**. An ESLint config alone no longer
starts background linting or selects ESLint for `warlock check`. TypeScript and
configured Oxlint remain the default health checkers; `warlock check` defaults
to Oxlint. An existing app can therefore lose its ESLint checks unless you
migrate or explicitly opt in.

Run **`warlock upgrade --from 5.32 --to 5.33.0`**, previewing with `--dry-run`
first. Section 2 has the dependency and review steps. Temporary legacy opt-ins
remain available, but their deprecation warnings name **5.34.0 as the removal
release**. New apps should use `--lint=oxc`.

### Rebuild before enabling PM2 readiness

Before using the new PM2 tooling, rebuild production bundles so completed boot
can send PM2's `"ready"` IPC message. Generate the ecosystem file with the target
`NODE_ENV`, review it, and run the built entry directly under PM2. PM2 is
installed separately; it is not a core dependency.

Fork reloads can interrupt traffic. Cluster sockets require a shared
`socket.adapter`, `socket.options.transports: ["websocket"]`, and WebSocket-only
clients. Socket.IO polling deployments need sticky routing to individual
listeners; do not treat cluster reload as an unconditional zero-downtime promise.

### Choose process memory limits for the deployment OS

The new `@warlock.js/process` supervises application-owned workers. Linux attempts
cgroup v2 enforcement before user code executes, with inherited rlimit/RSS
fallback. macOS and Windows support works without custom native code, but memory
caps are softer: macOS uses rlimit/tree RSS and Windows uses tree working-set
polling. **Windows Job Objects are not implemented yet.** Account for guardian
memory overhead; CPU limits are POSIX-only.

## 2. Breaking changes — exact steps when upgrading from 5.32

### Install the family together, then migrate to Oxlint/Oxfmt

1. Update every installed `@warlock.js/*` dependency to **5.33.0**, including
   development and optional dependencies. Use `create-warlock@5.33.0` for new
   apps. Keep the family versions aligned.
2. Ensure the new core release is installed and add the codemod dependency:

   ```bash
   npm install
   npm install -D ts-morph
   ```

3. Preview and apply the migration:

   ```bash
   npx warlock upgrade --from 5.32 --to 5.33.0 --dry-run
   npx warlock upgrade --from 5.32 --to 5.33.0
   ```

   Add `--json` to the preview for a machine-readable plan. Additions and
   deletions respect dry-run mode.

4. Review every reported `file:line`. The `oxc-toolchain` codemod replaces
   standard scripts and dependencies, pins TypeScript to **7.0.2**, migrates
   generated VS Code settings and literal checker switches, and deletes only
   recognized generated configs. A generated `.prettierignore` becomes
   `.oxfmtignore`; existing Oxc configs are preserved.

   Customized configs, editor settings, checker arrays, computed options and
   nonstandard scripts need manual translation. Preserved files are not proof
   that their old rules are active. Re-run the migration after addressing
   findings if needed; an app with only Oxc tooling is a no-op.

5. Install the changed dependencies, format and check the app:

   ```bash
   npm install
   npm run format
   npm run lint:check
   npx warlock check
   ```

   Then run your application's tests. Coming from 5.31 or earlier? Apply the
   earlier summaries' migrations too; this checklist covers 5.32 → 5.33.

### Temporary legacy opt-ins — removed in 5.34.0

| Where you still need ESLint | Explicit opt-in                              |
| --------------------------- | -------------------------------------------- |
| Development health checks   | `devServer.healthCheckers: { eslint: true }` |
| CLI checks                  | `warlock check --lint eslint`                |
| New legacy scaffold         | `create-warlock --lint=eslint`               |

Explicit ESLint opt-ins warn once per process on stderr with migration guidance;
the legacy scaffold and explicit Prettier compatibility scripts also warn about
removal in **5.34.0**. The legacy scaffold retains **TypeScript 6.0.3** for
compatibility; Oxc apps use **TypeScript 7.0.2**.

## 3. Behaviour changes that may break your app

These affect runtime behaviour or development workflows. Check each one you use.

| Change                                                                      | Who is affected                                          | What to check                                                                                                                                   |
| --------------------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| ESLint config detection no longer enables checks (`core`, `create-warlock`) | Existing apps relying on automatic ESLint selection      | Apply section 2 or explicitly opt in until 5.34.0; confirm your expected rules still run.                                                       |
| MCP cancellation suppresses the matching response (`ai-tools`)              | Served tools and clients using `notifications/cancelled` | Observe the per-call abort signal; cancellation is scoped to the matching caller/request, not every call with the same ID.                      |
| MCP policy runs after input validation (`ai-tools`)                         | Servers adding `beforeCall`                              | Invalid input skips policy. Return a native error refusal or throw a JSON-RPC error to deny; keep identity in context rather than tool input.   |
| Live page data re-runs the loader pipeline (`web`)                          | Pages opting into `config.live`                          | Refreshes bypass page caches and wait for navigation and unsent `<Form>` input; check CDN bypass and shared cache/socket adapter configuration. |
| Secret fakes join default test setup (`core`)                               | Tests using the new `secrets` facade                     | `secretsFake` isolates storage in memory. Use `tests.fakes: { secrets: false }` for intentional real-backend tests.                             |
| PM2 readiness follows completed boot (`core`)                               | Apps enabling `wait_ready` or cluster reloads            | Rebuild, review shutdown/startup timeouts, and configure cluster socket transport correctly.                                                    |
| Process resource enforcement differs by OS (`process`)                      | Apps deploying supervised workers across platforms       | Size memory headroom for fallback enforcement and guardian overhead; Windows has no Job Objects yet.                                            |

## 4. Defects fixed

| What broke                                                  | What it looked like                                                                                        | What changed                                                                                                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Socket-only connector startup (`core`)                      | Application readiness could be announced before the listener was ready or a bind failure was reported      | Boot now awaits the listener and rejects bind failures before readiness.                                                              |
| Live refresh during navigation or editing (`web`)           | A background refresh could race navigation or apply stale data after form editing began                    | Refreshes wait for navigation, recheck the current page's tags, and discard in-flight results when editing begins.                    |
| Live-refresh cleanup (`web`)                                | Cleanup used a control-flow override that could mask the refresh outcome                                   | Cleanup no longer overrides control flow.                                                                                             |
| Strict socket, keyring and MCP typings (`core`, `ai-tools`) | Async server startup and test fixtures failed strict typechecking; MCP specs mishandled string request IDs | Socket server types, declaration-safe keyring doubles, indexed access and request ID fixtures are corrected.                          |
| Snippet-gate temporary files (`tools/release`)              | A failed snippet run left scratch files that a toolchain script test treated as workspace packages         | Temporary files are always removed after diagnostics; toolchain tests ignore scratch directories and files without package manifests. |
| Frozen documentation sidebar                                | A latest-only entry leaked into a frozen version's navigation                                              | The sidebar leak is corrected.                                                                                                        |

## 5. New in 5.33.0

### MCP serving request context

`ai.mcp.serve(...)` exposes per-call **`requestId`**, authenticated **`principal`**,
and cancellation-aware signals over HTTP and stdio. `ToolContext` gains optional
identity fields, keeping authenticated identity out of tool input and model
messages.

HTTP `auth.authenticate` resolves the principal alongside existing bearer and
authorize checks; all configured checks must pass. Stdio accepts a static
principal or a per-request provider. `beforeCall` runs after input validation
and can allow the call, return a native error refusal, or throw a JSON-RPC error.
`notifications/cancelled` aborts only the matching caller/request and suppresses
its response even if the tool later finishes.

### Live page data over sockets, with polling fallback

Opt a page into dependency-based loader refreshes:

```tsx
import type { PageConfig } from "@warlock.js/web";

export const config = {
  live: { tags: ["products"], pollInterval: 15_000 },
} satisfies PageConfig;
```

Bind an existing app-owned client with `configureLivePageData({ socket })`.
After a write, `invalidatePageCache(["products"])` evicts cached data and broadcasts
dependency tags through core's socket adapter. It requires a configured cache
driver. Without a connected configured socket, clients poll instead.

Live requests run normal middleware/session/loaders and bypass page caches.
Refreshes wait for navigation and dirty `<Form>` controls; editing also discards
in-flight results. Multiple processes need a shared cache, stable page-cache
namespace and shared socket adapter. Publishing workers must boot the socket
connector to push updates; cache access alone does not deliver notifications.

### App-scoped secrets in core

Use `secrets.get/set/remove/has` from `@warlock.js/core` or
`@warlock.js/core/secrets`. `environmentName` provides the exact scoped environment
variable name. There is no separate secrets package.

Reads support a lazy optional OS keychain, read-only scoped environment lookup,
and authenticated encrypted owner-only files. File fallback needs the app's
encryption key; on Windows it fails closed because filesystem modes cannot
enforce owner-only ACLs there. Use keychain or environment storage on Windows.
Keep a stable namespace across changing release directories and migrate stored
values before changing namespace or encryption key.

Typed errors avoid exposing credentials. Encountered secrets register with the
logger for process-lifetime masking of keys, literal values, free text and Error
causes, including custom-censor paths. This does not cover direct console or
third-party logging. Explicit memory backends and the default `secretsFake`
support isolated tests without touching real credentials.

### Devtools AI panel on Panoptic traces

The dashboard at `/__warlock` adds an AI panel and AI runs inside HTTP request
details, powered by optional `@warlock.js/ai-panoptic`. It shows models,
token/cache usage, historical costs, tool timings, retries, truncation and
compaction metadata, with install guidance when Panoptic is absent.

Panoptic adds `subscribeTraces(listener)` for finalized process-local traces and
exact `requestId` filters for in-memory and cache-backed queries/aggregates.
Listener failures are isolated. Devtools retains bounded content-free traces
behind its development/loopback guard; Clear and connector shutdown clean up
dashboard retention independently of application exporter/cache stores.

### Measure AI input before running it

`ai.measure({ model, tools?, system?, messages?, skills? })` and standalone
`measure` report per-part input tokens, labelled as native counts or estimates,
and uncached input USD when prices are configured. `measure.diff(before, after)`
returns signed part/total changes and retains both reports. Compact tool schemas
and catalogue-only skill measurement help compare prompt overhead.

```bash
warlock ai measure --model "$MODEL_ID" --tools ./measure-tools.ts --system ./system.md --skills ./agent-skills --json
```

The CLI loads AI lazily without app bootstrap and supports configured model
modules. Native counting may use the network; unsupported count shapes fall
back to estimates for the entire report, while other provider errors propagate.
Reports mark the explicit probe used when messages are absent. Costs cover
uncached input only; output, cache adjustments and hosted-tool fees are excluded.
Skill bodies and library tools are not added automatically.

### Optional PM2 deployment commands

`warlock pm2 init` generates `ecosystem.config.cjs` from app/build config with a
`<project>-<app>-<env>` name, readiness URL, `wait_ready`, startup timeout and a
kill timeout matched to `app.shutdownTimeout`. Fork mode is the default.

`warlock pm2 reload [--id <pm2-id>]` verifies the exact app name, working directory
and bundle path, then reloads numeric PM2 IDs sequentially. Completed boot sends
PM2's `"ready"` message without disconnecting IPC; the existing `warlock start`
readiness protocol remains supported. Cluster workers skip exclusive port
preflight so they can share the primary's listener during rolling reloads.
Apply section 1's rebuild and socket requirements before deployment.

### New package: `@warlock.js/process`

```bash
warlock add process
```

The generator installs the exact family dependency and creates typed supervisor
config, boot recovery/shutdown hooks and optional devtools registration. Repeated
generation is idempotent. The read-only Processes panel and guarded
`/api/processes` endpoint discover that registration in development.

The supervisor owns the processes it launches, using random environment tokens
and PID/start-time identity for safe recovery and group stops. It supports label
filtering, streamed worker handles, exit reasons, peak memory, timeouts and
shutdown cleanup. Optional terminals load `node-pty` lazily.

Linux attempts cgroup v2 before user code, with rlimit/RSS fallback. macOS uses
`ps` creation identity and a live Node guardian's inherited token. Windows uses
PowerShell/CIM creation identity, the guardian token, PID-only `taskkill /T /F`
tree stops and working-set polling, with optional ConPTY terminals. macOS and
Windows need no custom native supervision code; their softer memory enforcement
and the absence of Windows Job Objects remain deployment limits.

## 6. Verification

All checks ran once on the final tree, on **Node 22.15**, each through a memory-
and CPU-capped runner, one at a time.

- **Install:** frozen install passes.
- **Typecheck:** 0 errors.
- **Tests:** 1,563 files; **17,500 passed, 0 failed, 23 skipped**.
- **create-warlock standalone:** 438 passed. **Release-tool tests:** 278 passed.
  **Script tests:** 22 passed.
- **Skill snippets:** 21/21 allowance. **Strictness:** within budget;
  `ai-tools` allowance lowered from **68 to 61**.
- **Docs build:** 913 pages. **Format, lint, public text, spec coverage and MDX
  guards:** clean; lint reports 0 errors.

The first validation found and fixed socket connector typing, a keyring fixture
type, MCP spec typing, ai-tools spec strictness, a CLI option list, a
live-navigation race spec, a web skill example, a toolchain script test reading
the snippet gate's temporary folder (the gate now always cleans up), a docs
sidebar leak, and one lint error. The results above describe the final tree
after those corrections.

**Not verified:** native Windows/macOS process supervision ran only through
unit-tested command/parsing helpers on Linux. OS keychain backends were tested
with a fake keyring module. Live page data cross-process delivery depends on
the application's socket adapter; the local checks do not establish delivery
for a deployment's adapter configuration.
