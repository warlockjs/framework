Grimoire adds two commands to the Warlock CLI, `warlock grimoire` and `warlock scry`, and the same questions as MCP
tools for coding agents.

## Register the commands

Add one line to `warlock.config.ts`:

```ts title="warlock.config.ts"
import { defineConfig } from "@warlock.js/core";
import { registerGrimoireCommands } from "@warlock.js/grimoire/warlock";

export default defineConfig({
  cli: {
    commands: [registerGrimoireCommands()],
  },
});
```

`registerGrimoireCommands()` returns two commands (`grimoire` and `scry`). An entry of `cli.commands` may be an
array, so the call sits next to your other commands as one entry. The same line brings the MCP tools and lets
`warlock explain` describe `GR` codes.

The module is light: it loads the book builder, the check and `@warlock.js/core/tooling` only when a command or tool
runs, so `warlock.config.ts` stays fast to load.

### Options

`registerGrimoireCommands(options)` and `createWarlockAdapter(options)` take:

| Option    | Default                                                  | Meaning                                                                                                                                                                                                                                              |
| --------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mobile`  | every top-level folder with `app.json` or `app.config.*` | Mobile apps in the repository: `{ root, id?, routing? }`. An app is file-routed when its `package.json` lists `expo-router` (screens come from its files), and code-navigated otherwise (you declare its screens in `grimoire/apps/<app>/screens/`). |
| `inspect` | the `warlock inspect` boot pass                          | How the facts that need the app booted (routes, events, jobs) are read.                                                                                                                                                                              |

## When the app boots

`warlock grimoire build` and `warlock grimoire check` first make sure the book exists and is fresh. Only changed files
are read again; an unchanged project reads nothing and writes nothing. `warlock scry` and the MCP read tools only read
the stored book (see [`warlock scry`](#warlock-scry)).

Route facts (routes, events and jobs) need the app booted, the way `warlock inspect` boots it: connectors boot, none
starts, no database connection opens and no port is bound. They are cached in the book and read again only when a
routes file, a file it imports, a config file, a mail, job, event or notification file, `warlock.config.ts` or
`package.json` changed.

- `warlock grimoire build` and `warlock grimoire check` boot the app only when the route facts are stale or missing.
  When the app does not boot, they go on with the cached route facts and print a `GR8002` warning. This holds when the app's config or bootstrap fails while the command starts, not only when its routes cannot be read.
- `warlock scry` and the MCP tools never boot the app. They use the cached route facts and add a note when they are
  stale. A route question of a project with no route facts stops with `GR9002` (a page or screen URL is still found);
  run `warlock grimoire build` first.
- An app with several sites (`src/web/$sites/<site>`) loads only `src/config/web.ts` for file questions, because the
  sites' base paths shape the page routes.

## `warlock grimoire build`

```bash
npx warlock grimoire build            # bring the book up to date
npx warlock grimoire build --force    # rebuild every entry and read the routes again
npx warlock grimoire build --site     # also write the static site to grimoire/book/site
npx warlock grimoire build --site --out public/grimoire
npx warlock grimoire build --site --product   # the business export: the Product map only
npx warlock grimoire build --json
```

```
book      35 files (46 written, 0 removed), routes fresh
features  3 (bookmaps written: 9)   tasks  1 open, 1 waiting, 1 done
time      0.4s
```

The summary is always the last lines, after any output the app prints while it boots. A run with nothing to do prints `book      up to date`. A task waiting for the owner is counted under `waiting`
only, not under `open`. `--site` writes the same view as the devtools tab as one
static `index.html` (see [Devtools](/v/latest/grimoire/guides/09-devtools/)); `--out` takes a folder inside the
project; a folder outside it, or the project folder itself, stops the command with `GR9006`. `--json` prints `{ rebuilt, changed, written, removed, routes, site, siteUpToDate, siteMode, problems }`.

`--site --product` writes the business export: the Product map as a read-only page, opening on the map, with no
file paths, test names, export names, check findings or per-file answers (the same detail a share link hides). It is
much smaller than the full export, because it carries no per-file answers and no code search; the screenshots the
written files use are copied next to it. Hand this one to people who do not read code. The full export stays the
developer view.

A site export carries a stamp of the book it was built from (the code and test files, the written folders, the test
results). When the folder already holds a page with the same stamp and mode, `build --site` does not write it again
and prints `(up to date, not rebuilt)`; `--force` writes it anyway.

## `warlock grimoire check`

```bash
npx warlock grimoire check
npx warlock grimoire check --all     # list every finding
npx warlock grimoire check --json
```

```
grimoire/features/catalog/flows/browse-products.md:26  GR4001  warning  catalog/browse-products AC-1 has no test
…
    … GR4001: 12 findings in all, 7 not shown
grimoire/features/catalog/flows/wishlist.md:12  GR2001  error  route step "POST /api/wishlist" matches no route  (expected)
7 findings not listed; run with --all to list every finding.
0 errors, 8 warnings, 8 expected  (routes: fresh)
book      up to date
time      0.3s
```

Errors always print in full. When a code has more than five warnings, the text shows the first five, then how many
are left. `--all` prints every finding; `--json` is always complete. The last two lines (the book state and the
time) come after the app's own boot output.

The command exits 1 only when the report holds an error that is not expected. Findings on proposed features and
flows are expected and never fail it. [The check](/v/latest/grimoire/guides/04-check/) lists every code.

## `warlock grimoire release <release>`

```bash
npx warlock grimoire release 1.1.0
```

```
grimoire/releases/1.1.0.md: 1 entry collected (catalog 2.1 fixed)
note: 1 entry is still unreleased: orders 3.0. To ship them in 1.1.0, move them under "## 1.1.0 (2026-11-20)" in each feature's CHANGELOG.md and run this command again.
```

It writes the list of the changelog entries stamped with that release between the markers of
`grimoire/releases/<release>.md`, and changes nothing else. Write the release file (front matter `release` and
`date`, and the brief) first: without it the command stops with `GR9005`. Broken markers stop it with `GR1024`. See
[Tasks and releases](/v/latest/grimoire/guides/06-tasks-and-releases/).

### Stamp and collect: `--stamp`

```bash
npx warlock grimoire release --stamp
npx warlock grimoire release 1.4.0 --stamp --date 2026-11-24
```

```
stamped catalog, orders → 1.4.0 (2026-11-24)
wrote grimoire/releases/1.4.0.md
grimoire/releases/1.4.0.md: 2 entries collected
```

With `--stamp` the command does the agent's release steps first, then collects as above:

- The version is the argument, or the `version` of the app's `package.json`. The date is `--date`, else the date of the
  release file when it exists, else today.
- In each feature `CHANGELOG.md` that has entries under `## Unreleased`, the entries move under a new
  `## <version> (<date>)` heading and an empty `## Unreleased` stays above it. No other byte of the file changes.
- When `grimoire/releases/<version>.md` is missing, it is written with its front matter, a `# Release <version>`
  heading and a one-line brief that names the changed features. Rewrite the brief in your own words; a release file
  that exists is never touched, and neither is its brief.
- It stops with `GR9006` and changes nothing when the version is missing (no argument and no `version` in
  `package.json`), when the date is not `yyyy-mm-dd`, or when a section for the version exists with another date or the
  release file has another date than `--date`.
- `--json` prints `{ stamped, created, collect }`: the features stamped, the release file written (or `null`) and the
  collect result.

The stamp is the only edit Warlock makes to written files, and only when you ask for it with `--stamp`. Without
`--stamp` the command writes the collected list and nothing else.

## `warlock grimoire guard [task]`

Checks the change (the git diff against a base) against its task: files outside the task's features, removed flows,
criteria and cases, deleted proving tests, edited locked tests, protected areas and the code rules on the lines the
change adds. See [Drift controls](/v/latest/grimoire/guides/11-drift-controls/) for what each finding means.

```bash
warlock grimoire guard                # the one task in progress
warlock grimoire guard T-12           # T-12, 12 and T-012 name the same task
warlock grimoire guard T-12 --base origin/main
warlock grimoire guard --base origin/main --commits origin/main..HEAD
warlock grimoire guard --hook         # for an agent's Stop hook
warlock grimoire guard --json
```

| Option              | What                                                                                                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[task]`            | The task id. Without it the guard uses the tasks named in the commits of `--commits`, then the one task whose status is `in progress`, else `GR9008`.                                                               |
| `--base <ref>`      | The ref the change is compared with. Default: the point where `HEAD` left the default branch (`origin/HEAD`, then `main`, then `master`), else `HEAD`.                                                              |
| `--commits <range>` | A commit range (`origin/main..HEAD`). Every commit must name a task id (`T-12`) that has a file (`GR7012`); the tasks the commits name are guarded.                                                                 |
| `--hook`            | Agent-hook mode: everything goes to stderr, exit code 2 on an error, 0 otherwise, also when no task or no git repository is found and when the hook input says the agent already went on once (`stop_hook_active`). |
| `--json`            | Print the report as JSON.                                                                                                                                                                                           |

The change is every file that differs between the base and the working tree: committed, staged, unstaged and
untracked (not ignored). The guard never boots the app and reads the route facts of the last build.

Text output is one line per finding, as `warlock grimoire check` prints them (`<file>:<line>  <code>  <severity>  <message>`
and a `fix:` line under each error), then `not approved: <n> changes` with one line per change since the approved
baseline that nobody approved (these never fail the guard), then `guard: ok` or `guard: <n> errors`.

Exit codes: `0` no error, `1` at least one error, `2` an error in `--hook` mode. `GR9009` (git could not answer) and
`GR9008` (no task) exit `1`, and `0` in `--hook` mode.

`--json` prints:

```json
{
  "schemaVersion": 1,
  "task": "T-20",
  "base": "9f1c2e…",
  "changed": [
    { "file": "src/app/orders/utils/extra.ts", "status": "added", "from": null, "addedLines": [1] }
  ],
  "findings": [
    {
      "code": "GR7006",
      "severity": "error",
      "message": "…",
      "at": { "file": "…", "line": 1, "column": null },
      "expected": false,
      "subject": { "feature": null, "flow": null, "app": null, "task": "T-20", "file": "…" },
      "hint": "…"
    }
  ],
  "notApproved": [],
  "counts": { "errors": 1, "warnings": 0, "expected": 0 },
  "ok": false
}
```

`base` is the commit the change was compared with; `task` is `null` when none was found, and joins several ids with a
comma when the commits name several.

### `warlock grimoire approve api`

Writes the routes the book knows to `grimoire/approved/api.json`, the approved public API. It reads the route facts of
the last `warlock grimoire build` and never boots the app. `warlock grimoire check` warns (`GR7013`) when the routes
differ, and the guard reports `GR7011` for a change that does not name `public-api` in `Touches:`.

## `warlock grimoire approve <target>` and `reject <target>`

The owner accepts or refuses a change since the approved baseline: a new or changed capture, a removed image, a new or
removed flow, criterion or case, a criterion that lost its proving test.

```sh
npx warlock grimoire approve shot-changed:contact/send-message:AC-2:ar   # one change, by its id
npx warlock grimoire approve contact/send-message --lang ar              # every change of a flow, one language's images
npx warlock grimoire approve --all                                       # everything; creates the baseline the first time
npx warlock grimoire reject contact/send-message --note "the button is too small"
```

The target is a change id (the ids are in the `check` messages and the Bird view), a `<feature>/<flow>`, or `--all`.
`--lang` keeps only the images of one language. A target nothing matches is `GR9010`. Text output prints one line per
change and then `approved <n>` (or `rejected <n>`); `--json` prints `{ "done": [...] }`. `approve --all` with no
baseline creates it from the current state. Approving copies the capture to `grimoire/screenshots/approved/` and
updates `grimoire/approved/baseline.json`. See
[Screenshots and approvals](/v/latest/grimoire/guides/12-screenshots-and-approvals/).

## `warlock scry`

One question at a time. Text by default, `--json` for the result object. Paths may use either separator and may be
absolute.

`scry` only reads. It answers from the book the last `warlock grimoire build` left in `grimoire/book/` and never
rebuilds it, never boots the app and never writes a file, so a call on a large app takes a fraction of a second. Run
`warlock grimoire build` after you finish editing. While the code, test or written files differ from the book, every
answer ends with a note (in `--json`, the `notes` list), and the answer is the stored one:

```
note      book is stale (12 files changed); run warlock grimoire build
```

A project whose book was never built (or was built by another version) stops with `GR9007`.

### A file

```bash
npx warlock scry src/app/catalog/services/new-arrivals.service.ts
```


same page URLs and an optional `site`.

### Errors under `--json`

With `--json`, a failed `scry` prints the error as JSON on stdout and exits 1, so a caller that parses stdout always
gets an object:

```json
{
  "type": "error",
  "code": "GR9002",
  "message": "No route matches DELETE /api/orders. …",
  "fix": "…"
}
```

`fix` is the code's fix text (an empty string when it has none). Without `--json` the error is text on stderr, as for
every command. The `ScryError` type describes the object; the scry MCP tools return the same object as their error
text (see [MCP tools](#mcp-tools)).

### Search: `--search`

```bash
npx warlock scry --search "the change history screen needs a better ui"
npx warlock scry --search "new arrivals"
npx warlock scry --search "order" --limit 5 --app mobile
```

```
 21.4  flow     catalog/new-arrivals              New arrivals
 12.9  block    mobile/home/new-arrivals          catalog/new-arrivals
 11.3  route    GET /api/products/new-arrivals    catalog.new-arrivals
  9.8  file     src/app/catalog/services/new-arrivals.service.ts  Lists the newest products sold in the customer's country.
changes with the top hits:
  src/app/catalog/repositories/products.repository.ts   imported by new-arrivals.service.ts
  src/app/catalog/tests/new-arrivals.test.ts            test
next: warlock scry --impact src/app/catalog/services/new-arrivals.service.ts
```

Search first, then run `--impact` on the top hit (the `next:` line). Pass the whole sentence (a commit title, a bug report) rather than two keywords: a hit needs only some of the words,
and more words give the right file more to match. Case does not matter, words are matched whole (`ui` does not find
`build`), a plural or `-ing`/`-ed` form matches its base word, and small words such as `the`, `of` and `for` are left
out (a text of small words only finds nothing). An id such as `AC-5` or `WL9003` stays one word.

Search reads any language. One tokeniser serves the text and the index: accents and Arabic vowel marks are dropped
(`café` and `cafe` match, so do `أحمد` and `احمد`), the tatweel is dropped, `ى` is read as `ي` and `ة` as `ه`, words
split at every character that is not a letter or digit, camel case splits in any script, and an Arabic word of five or
more letters loses a leading article (`ال`, `وال`, `بال`, `لل`), so `شحنة` finds `الشحنة`. A few Arabic small words
(`في`, `من`, `على`) are left out like the English ones. Stemming of plurals and `-ing`/`-ed` is for Latin words only.
A text with no letters or digits in any script stops with `GR9006`.

Hits are ranked in two tiers and printed in score order, best first, with the score in front of each line:

1. **Names first.** A feature, flow, block, page, route, file or export whose name or title is the whole text ranks
   highest, then one that starts with the text, then one that holds every word as a whole word. A feature or flow
   adds two ranks to such a match.
2. **Everything else by BM25F score.** Candidates that share only some of the words are scored over four fields:
   the words of the id or path (weight 3), export names (2), the header sentence or title (1) and written text (1:
   a flow's summary, story, cases and criteria). Rare words count more than common ones. A block is found through
   its `<app>/<page>` and its text, never through the slug of its whole text.

Name matches always rank above scored matches. On an equal score features and flows come first, then a page or screen
file before its helper files. A flow found by its written text shows the part that matched, like
`[AC-5: A receipt is emailed]`. Page, screen, block and file hits carry the `app` they belong to; `--app <id>` keeps
only the hits of that app (features, flows, routes and tasks belong to none and are left out). When the limit cuts the
list, a last line counts the matches per type (`showing 20 of 41 (2 flow, 39 file); raise --limit for more`), and
`--json` carries the same `counts`. The index is built once for each opened book, so repeated searches in the MCP
server stay fast. `--limit` defaults to 20.

#### What changes with the top hits

After the hits, the answer lists the files that usually change with the top ones, so you open the right files
without a second question. They come from the top three hits that map to files (a file, an export, a page or screen, a
mail or job, a route's handler, or the files a flow's steps start from). For each, the list holds the files it imports
and the files that import it when they belong to the same feature (the same module when the file has no owner), no
specs, plus the spec files that import it and the tests that prove a hit flow's criteria. Files are ranked by how many
of the top hits share them, then step files, importers, imports and tests, and the list stops at 10 files whatever the
`--limit`. A file that is already a hit is left out.

Each line says why the file is there: `imports <hit file>` (it imports the hit's file), `imported by <hit file>` (the
hit's file imports it), `test`, or `step of <flow>`. The last line, `next: warlock scry --impact <file>`, names the
impact question for the first file. In `--json` the answer carries `alsoChanges` (`{ file, reason, via }`, `via` being
the ids of the top hits that brought the file in), `weak` and `next`.

When the best hit is not a name match and holds fewer than half of the words of the text, the answer is marked weak
(`"weak": true`) and ends with `weak match: no hit holds most of the request's words; use grep for literal text`.
Use grep for literal text and when the answer says this.

Spec files, locale files and type files have their BM25F score multiplied by 0.6, so code wins a near tie and they are
still found when nothing else matches.

### Errors

Every error prints its code, what failed and what to do, and the command exits 1:

```
GR9003  No feature has the id "billing". Features: auth, catalog, orders.
  fix: Use an id from `grimoire/features/`.
```

| Code     | When                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------- |
| `GR9001` | The file is not in the book (not a code file under the source roots, or new since the last build). |
| `GR9002` | No route matches, or there are no route facts yet.                                                 |
| `GR9003` | No feature has that id.                                                                            |
| `GR9004` | No flow has that id.                                                                               |
| `GR9006` | The question is missing, asks two things at once, or has the wrong form.                           |
| `GR9007` | The book was never built, or was built by another version: run `warlock grimoire build`.           |

## MCP tools

`warlock mcp` and `warlock dev --mcp` serve these tools next to the built-in ones. They answer with the same objects
`--json` prints. The read tools never boot the app; they use the cached route facts, and a `grimoire_route` question
on a project with no route facts stops with `GR9002` (pages and screens are still found by their URL).

| Tool               | Input                              | Answer                                                 | Writes |
| ------------------ | ---------------------------------- | ------------------------------------------------------ | ------ |
| `grimoire_file`    | `{ file }`                         | the file answer                                        | no     |
| `grimoire_impact`  | `{ file }`                         | the impact answer                                      | no     |
| `grimoire_route`   | `{ method, path, site? }`          | the route answer                                       | no     |
| `grimoire_feature` | `{ feature }`                      | the feature answer                                     | no     |
| `grimoire_flow`    | `{ flow, files?, step?, offset? }` | the compact flow answer, or one page of a step's files | no     |
| `grimoire_search`  | `{ text, limit?, app? }`           | the search answer                                      | no     |
| `grimoire_check`   | `{}`                               | the check report (`note` when the book is behind)      | no     |
| `grimoire_build`   | `{ force? }`                       | `{ rebuilt, written, removed, routes, note? }`         | no     |
| `grimoire_release` | `{ release }`                      | the release file, its list and whether it changed      | yes    |
| `grimoire_explain` | `{ code }`                         | the code's title, fix, skill and docs link             | no     |

When a question fails, the scry tools (`grimoire_file`, `grimoire_impact`, `grimoire_route`, `grimoire_feature`,
`grimoire_flow`, `grimoire_search`) return a tool error whose text is the same `ScryError` JSON that `warlock scry --json`
prints, so a client can parse the code and the fix:

```json
{ "type": "error", "code": "GR9004", "message": "No flow catalog/returns. …", "fix": "…" }
```

The other tools' errors read `GR9006: <message> Fix: <fix>`.

`grimoire_flow` answers with counts instead of file lists: each step has `counts` (`direct`, `feature`, `reachable`,
`typeOnly`) and its first 50 direct imports, so the answer stays small on a large app. To see the files behind one
step, call it again with `files` (`reachable` or `type-only`) and `step` (the step number); a page holds 200 files
sorted by module, and `offset` moves to the next page. `warlock scry --flow --json` and the `scry()` function keep the
full lists.

The MCP server keeps the opened book in memory between calls. Each read tool checks that nothing changed with a stamp
of `stat` results (the size and modified time of the code and test files, the folders that hold them, every written
file, the manifest and the test results file; no file is read) and answers from the kept book when the stamp is the
same. A change to a code file, a written file or the manifest opens the book again on the next call, so answers never
go stale. On a large app this turns a call that reopened the book (seconds) into a stat pass over the files (a fraction of a
second). The read tools open the stored book the way `warlock scry` does: they never rebuild it, and say in `notes` when it is behind the files. `warlock scry` as a one-off command opens the stored book once per process; the kept book helps long-running processes.

The read tools write nothing. `grimoire_build` refreshes the book, which is a git-ignored cache, so it does not count as
a write. `grimoire_build` reads the routes again when they changed (under `warlock mcp` this boots the app once, the
`warlock inspect` way). `grimoire_release` writes a project file, so the server refuses it unless it runs with
`--allow-writes`.

## From code

```ts
import { createWarlockAdapter, collectMobileFacts } from "@warlock.js/grimoire/warlock";
import { openGrimoire, scry, formatScryResult } from "@warlock.js/grimoire";

const root = process.cwd();
const snapshot = await openGrimoire(root, createWarlockAdapter(), { routes: "cached" });

console.log(
  formatScryResult(scry(snapshot, { type: "flow", feature: "catalog", flow: "new-arrivals" })).join(
    "\n",
  ),
);
console.log(await collectMobileFacts(root));
```

`openStoredGrimoire(root, adapter)` opens the book the last build left without building it, the way `warlock scry`
does (`GR9007` when it was never built). `SCRY_STOP_WORDS` is the set of small words search leaves out; add a word to
it before the first search of a process to leave that word out too:

```ts
import { SCRY_STOP_WORDS } from "@warlock.js/grimoire";

SCRY_STOP_WORDS.add("please");
```

`createWarlockAdapter(options)` turns the inspect report into the book's facts: files from `collectFiles()` of
`@warlock.js/core/tooling` (over `src` and each mobile app's source folders, leaving out `android/`, `ios/` and
build output), routes, events and jobs from `inspectApp()`
after the boot pass, pages from the web page graph, and mobile apps from their folders (`collectMobileFacts()`).
`reachedFrom` of a page is `null` (unknown) for now. Mails are files named `*.mail.ts` or `*.email.ts` and files in a `mails/` or `emails/` folder; notifications are
files named `*.notification.ts`. Jobs are the names of the queue's registry (`defineJob()`) and of the scheduler's
scheduled tasks, plus any `*.job.ts` file the registries do not list.
