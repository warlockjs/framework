`warlock grimoire check` reads the written files, the book and the tests, and reports every place where they
disagree: a step that names a route that does not exist, a criterion no test proves, a file no feature owns. It
only reads. It never changes a written file or a source file.

```bash
npx warlock grimoire check
npx warlock grimoire check --all     # list every finding
npx warlock grimoire check --json
```

## The output

One line per finding, then the counts:

```text
grimoire/features/auth/flows/login.md:29  GR4001  warning  auth/login AC-1 has no test
grimoire/features/catalog/flows/browse-products.md:26  GR4001  warning  catalog/browse-products AC-1 has no test
grimoire/features/catalog/flows/new-arrivals.md:30  GR4001  warning  catalog/new-arrivals AC-3 has no test
grimoire/features/catalog/flows/wishlist.md:12  GR2001  error  route step "POST /api/wishlist" matches no route  (expected)
grimoire/features/catalog/flows/wishlist.md:13  GR2004  error  notification step "wishlist-price-drop" matches no notification  (expected)
grimoire/features/catalog/flows/wishlist.md:30  GR4001  warning  catalog/wishlist AC-1 has no test  (expected)
0 errors, 3 warnings, 3 expected  (routes: fresh)
```

- Each line is `<file>:<line>  <code>  <severity>  <message>`. A finding with no single place shows `-`.
- Under each error that is not expected, a line `    fix: …` says what to do.
- Problems come first: errors, then warnings, each by file and line. Expected findings come last.
- The last line counts the errors and warnings that are not expected, and the expected findings. It also says how
  fresh the route facts were.
- Errors always print in full. When a code has more than five warnings, the text shows the first five of that code,
  then `… GR3001: 6547 findings in all, 6542 not shown`, and a line says how many findings were not listed. A
  project with no written files yet therefore prints a few lines per code, not thousands. `--all` lists every
  finding.
- The last lines are the book state and the time, after any output the app printed while it booted.
- `--json` is always complete. It prints the report object: `findings` (each with `code`, `severity`, `message`, `at`, `expected`,
  `subject` and `hint`), `counts`, `ok` and `routes`.

The command exits with code 1 when there is an error that is not expected, and 0 otherwise. Warnings never fail it.

## Expected findings

A feature or flow with `status: proposed` describes work that is not built yet, so its routes, pages and tests do
not exist. Every finding about it is marked `(expected)`: it is listed so you can see what is still to build, and it
never fails the check. Once the code exists, set the status to `building` or `shipped`; from then on the same
findings are problems.

## Route facts

Route steps, and mail, job, event and notification steps, are checked against facts that need the app to boot. The
check refreshes them when the routes files changed (`routes: fresh`). A route step matches a route the same way
`warlock scry --route` does: params written either way (`:id` or `[id]`), a trailing `/` ignored, the method in any
case, and `ALL` matching any method. `GR2001` means no route matches that way.

- When they are older than the routes files (`routes: stale`), the steps are checked against the cached facts and
  the report adds `GR8003`.
- When there are none (`routes: missing`, the app did not boot), those steps are not checked. `GR8002` says why.
  Page steps and `affects` steps are always checked.

## What it checks

| Area          | It reports                                                                                                 | Codes              |
| ------------- | ---------------------------------------------------------------------------------------------------------- | ------------------ |
| Written files | a file that does not follow its template                                                                   | `GR1001`–`GR1028`  |
| Steps         | a route, page, mail, notification, job, event or flow that does not exist                                  | `GR2001`–`GR2007`  |
| App names     | a feature, flow, criterion or task naming an app with no folder, or one its feature does not list          | `GR2008`, `GR2009` |
| References    | a changelog entry or README relation naming a flow or criterion that does not exist                        | `GR2010`–`GR2012`  |
| Source files  | no header sentence, no feature, two owners, a wrong `@feature` tag or folder, a file no flow reaches       | `GR3001`–`GR3006`  |
| Tests         | a criterion with no test, a `@proves` line that names nothing or has the wrong form, failed or old results | `GR4001`–`GR4008`  |
| Apps          | blocks, conditions, pages, layouts and screens that point at nothing                                       | `GR5001`–`GR5009`  |
| Versions      | the README version or date out of step with the changelog, a release that does not match                   | `GR6001`–`GR6008`  |
| Tasks         | a task naming a feature or flow that does not exist, or in the wrong folder                                | `GR7001`–`GR7005`  |

Steps and criteria of a `retired` flow are not looked up: its code is gone on purpose.

A test proves a criterion with a line comment directly above it:

```ts
// @proves catalog/new-arrivals AC-2
it("returns the global list when the customer has no country", async () => {
  // …
});
```

The check reads these lines from the test files the book lists: spec files under the source roots,
`e2e/**/*.e2e.ts` and `tests/**/*.{test,spec}.ts` at the project root. Lines inside block comments are ignored. See
[Test results](/v/latest/grimoire/guides/08-test-results/) for the reporter that records their last results.

## Look up a code

```bash
npx warlock explain GR2001
```

It prints the title, the fix and the skill for the code. Every code is listed below.

## From code

```ts
import { checkGrimoire, formatCheckReport, openGrimoire } from "@warlock.js/grimoire";
import { createWarlockAdapter } from "@warlock.js/grimoire/warlock";

const snapshot = await openGrimoire(process.cwd(), createWarlockAdapter(), { routes: "cached" });
const report = checkGrimoire(snapshot);

console.log(formatCheckReport(report).join("\n"));
```

`scanProofsInText(text, file)` reads the `@proves` lines of one test file's text, and `scanProofs(root, files)` reads
them from a list of project-relative test files. Both return the proof lines and the `GR4003`–`GR4005` findings.

## Codes

Each code keeps its meaning across releases. An error fails the check unless it is expected; a warning never does.

## GR1xxx: written files

### GR1001

A written file has no front matter.

- **Severity:** error
- **What to do:** Start the file with the front matter block its template shows, between two `---` lines.
- **Skill:** `write-a-feature`

### GR1002

The front matter cannot be read.

- **Severity:** error
- **What to do:** Write one `key: value` per line; lists as `[a, b]` or as `- item` lines under the key; close the block with `---`.
- **Skill:** `write-a-feature`

### GR1003

A required front matter key is missing.

- **Severity:** error
- **What to do:** Add the key named in the message; the template of that file lists every required key.
- **Skill:** `write-a-feature`

### GR1004

A front matter value has the wrong form.

- **Severity:** error
- **What to do:** Use the form the message names: dates as yyyy-mm-dd, versions as 2.1, ids in lower-case-with-dashes, a status from the list (a task status is open, waiting for approval, approved, in progress, blocked, done or dropped; a question for the owner is waiting for approval).
- **Skill:** `write-a-feature`

### GR1005

A front matter key is not part of the template.

- **Severity:** warning
- **What to do:** Remove the key, or move what it says into the body of the file.
- **Skill:** `write-a-feature`

### GR1006

A required heading is missing.

- **Severity:** error
- **What to do:** Add the heading named in the message, spelled as in the template.
- **Skill:** `write-a-feature`

### GR1007

A heading is not part of the template.

- **Severity:** warning
- **What to do:** Use the template's headings; put the text under one of them or remove it.
- **Skill:** `write-a-feature`

### GR1008

A step line has the wrong form.

- **Severity:** error
- **What to do:** Write steps as `1. route   POST /wishlist`: a number, a kind, then the name used in code.
- **Skill:** `write-a-feature`

### GR1009

- **Severity:** error
- **What to do:** Use one of: page, route, mail, notification, job, event, outside service, affects.
- **Skill:** `write-a-feature`

### GR1010

- **Severity:** error
- **What to do:** Number the steps from 1 without gaps, in the order a user meets them.
- **Skill:** `write-a-feature`

### GR1011

- **Skill:** `write-a-feature`

### GR1012

- **Skill:** `write-a-feature`

### GR1013

- **What to do:** Write criteria as `- AC-3   a guest is sent to sign in`, optionally `- AC-4 [mobile]   …`.
- **Skill:** `write-a-feature`

### GR1014

A criterion id is used twice in one flow.

- **Severity:** error
- **What to do:** Give the new criterion the next free number. Never renumber existing criteria.
- **Skill:** `write-a-feature`

### GR1015

A changelog line has the wrong form.

- **Severity:** error
- **What to do:** Write entries as `- 2.1  fixed   new-arrivals: what changed (AC-2)`.
- **Skill:** `record-a-change`

### GR1016

A changelog entry uses an unknown word.

- **Severity:** error
- **What to do:** Use one of: added, changed, fixed, removed.
- **Skill:** `record-a-change`

### GR1017

A changelog heading has the wrong form.

- **Severity:** error
- **What to do:** Use `## Unreleased`, or `## <release> (<yyyy-mm-dd>)` for entries of a release.
- **Skill:** `record-a-change`

### GR1018

### GR1019

- **Skill:** `write-a-feature`
