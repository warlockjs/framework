# Warlock web — build RTL and mixed-direction UI

Read this after `localize-pages.md`, which owns dictionaries and the locale URL strategy. This topic covers what the page does with a direction once the locale is known.

## Direction comes from the locale

The server render sets `<html lang dir>` from the request's resolved locale. The default root does this; a custom `src/web/root.tsx` must follow the same rule (`write-the-root.md`). The browser cannot update the document from inside the hydrated tree, so after a client locale change the framework syncs `lang` and `dir` itself.

Inside pages, read the direction instead of recomputing it:

```tsx
import { useTextDirection, useTrans } from "@warlock.js/web";

export default function Banner() {
  const direction = useTextDirection(); // "rtl" | "ltr"
  const t = useTrans();

  return <aside dir={direction}>{t("banner.title")}</aside>;
}
```

`localeDirection(locale)` resolves the direction for any BCP 47 tag (script subtags win, so `az-Arab` is rtl). Use it for locale lists in a switcher, where each option needs its own direction.

## Layout uses logical properties

Write spacing, alignment and positioning in logical terms so one stylesheet serves both directions:

- `margin-inline-start` / `padding-inline-end` instead of `margin-left` / `padding-right`.
- `inset-inline-start`, `text-align: start`, `border-inline-start`.
- Flex and grid order follows `dir` automatically; avoid hard-coded `row-reverse` for locale switches.

Mirror only directional meaning: back and forward chevrons, progress direction, "next" arrows. Do not mirror brand marks, clocks, play icons, or icons whose orientation is universal. Mirror by CSS (`[dir="rtl"] .chevron { transform: scaleX(-1) }`) or a direction-aware icon component, not by duplicating markup.

## Translate every visible and spoken string

Translate first-party labels, placeholders, empty, loading and error states, page metadata, and accessible names (`aria-label`, `alt` on meaningful images, button text generated by components). A translated paragraph next to an English button is a bug. Each flattened key has one owner in `locales.json`; do not duplicate a label under two routes.

## Content direction is separate

The interface direction is the page's `dir`. User-written text can run in any direction, so:

- Give user text and comments `dir="auto"` so the browser picks direction from the first strong character.
- Isolate identifiers, usernames, timestamps and speaker labels inside a sentence with `<bdi>` or `dir="ltr"` on a span, so punctuation does not jump.
- Keep email, URL, code, phone and API-key inputs LTR where the content requires it (`dir="ltr"` on the input), without forcing the whole form LTR. Labels stay in the page direction.

## Dates, times and numbers

Format instants with an explicit locale and the user's timezone, and produce identical output on the server and in the first client render. A different default on either side causes a hydration mismatch.

Treat date-only values (a birthday, a due date) separately from instants: format them in UTC or as calendar fields, never by converting through the viewer's timezone, or they shift a day. Localized digits in input are a product choice; if you accept Arabic-Indic digits, normalize and validate them on the server too.

## Verify with real text

Test with actual Arabic copy and with mixed Arabic and English sentences containing emails, numbers and code. A mirrored sidebar alone does not prove RTL support. Check the keyboard path and focus order in both directions, and check that the browser's `lang` on `<html>` matches the page language so screen readers pick the right voice.

Keep fonts, palettes, calendar systems and digit policies configurable by the application; the framework does not choose them.
