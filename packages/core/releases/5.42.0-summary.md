# Warlock.js 5.42.0 — release summary

Released 2026-11-01.

All **33 packages** (`@warlock.js/*` and `create-warlock`) move to 5.42.0 together;
keep every family package on the same version. No breaking changes. This release adds
built-in security response headers and makes per-route body limits work in development
and tests.

---

## 1. Breaking changes

- **None.** The new security headers are on by default; see the upgrade notes if your app
  frames its own pages or lets an embedded third-party frame use the camera, microphone or
  location.

---

## 2. Security response headers on every response (`core`)

- `http.securityHeaders` sends, by default:
  - `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`, so no site
    can frame the app (clickjacking). `"self"` allows your own pages; a list allows named sites.
  - `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`.
  - `Permissions-Policy`: camera, microphone and geolocation only for your own pages; motion
    sensors and USB off. Merge your own per feature.
  - `Strict-Transport-Security: max-age=31536000; includeSubDomains` in production only
    (`preload` is opt-in).
- They are set in the server's first hook, so routed handlers, static files, 404s, early
  refusals (CORS, 413, 429), SSR pages and handlers that call `reply.raw.writeHead` all carry
  them, in production, `warlock dev` and the HTTP test server.
- Each header can be turned off with `false`, and `http.securityHeaders: false` turns them all
  off. A route can override or opt out with the `securityHeaders` route option, for example an
  embeddable widget.
- With `http.csp` on, the response carries one CSP header with `frame-ancestors` once; a
  `frame-ancestors` in `http.csp.directives` wins.
- Pages no longer log a React hydration mismatch on the framework's nonced `<script>` tags
  under a CSP header (browsers hide nonce values from the DOM). This also fixes apps that already
  used `http.csp` (`web`).

---

## 3. Per-route body limits in development and tests (`core`)

- A route's `serverOptions.bodyLimit` (for example 21 MB for a photo upload) now applies under
  `warlock dev` and the HTTP test server, not only in a production build: bodies within the
  route's limit are accepted, larger ones get the same `413` as in production, and other
  routes keep the server limit. Chunked bodies are counted as they stream.
- A route's `serverOptions.preParsing` hooks now run in the dev server too.
- The dev server logs one boot warning per route for any other `serverOptions` it cannot apply,
  so a difference from production is visible.
- Multipart uploads are bounded by `http.fileUploadLimit`, not `bodyLimit`, in every mode.

---

## 4. Upgrade notes

1. **Update the family.** Run `npx warlock update`.
2. **Read what changed.** Run `npx warlock release-notes --from 5.41.0`.
3. **Framing your own pages?** Set `http.securityHeaders.frameAncestors: "self"` (or a list of
   sites). An embeddable route can opt out with the `securityHeaders` route option.
4. **Remove workarounds.** A connector that set these headers by hand can go, and so can any
   release-only check of a route's body limit: it now works in tests.
