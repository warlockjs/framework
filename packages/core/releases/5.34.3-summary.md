# Warlock.js 5.34.3 — release summary

Released 2026-10-20.

All **33 packages** (`@warlock.js/*` and `create-warlock`) move to 5.34.3 together;
keep every family package on the same version. Existing apps need no code changes.

---

## 1. One concise agent skill per package

- **Every package exports exactly one skill named after it**: `warlock-js-core`,
  `warlock-js-ai-openai`, `warlock-js-sitemap`. The 14 single-topic packages
  previously exported names like `warlock-js-ai-openai-setup-openai`.
- **Every package description was rewritten to 450 characters or fewer** at the
  package level: what it is for, key exports, typical requests and "not this
  package" pointers. The 33 descriptions now total about 13,300 characters
  instead of about 22,900, inside the roughly 20,000 characters agents keep for
  skill descriptions, with room left for an app's own skills.
- The release check enforces one skill per package and the description cap.

Re-run `npx agent-kit sync` (or reinstall) after upgrading so agents pick up the
new names.

---

## 2. Starter project standards (`create-warlock`)

New apps get revised project skills:

- **web-code-standards:** one component per file, with hooks and helpers in
  their own files unless small and tightly coupled; every form uses Mongez
  React Form validation, never native browser validation; no native select,
  checkbox, radio or date inputs — custom accessible controls built on the
  project's UI kit (shadcn/ui when Tailwind and shadcn are installed, otherwise
  the agent asks which kit to use, with a recommendation).
- **api-design:** controller examples use the real `({ request, response })`
  signature; camelCase response fields through resource field mapping; one error
  shape, `{ error: { code, message } }`; `responseSchema` on controllers;
  `Idempotency-Key` for side-effecting endpoints; request IDs in errors.
- **code-standards and the other project skills:** shorter descriptions,
  references by skill name, resolved contradictions (barrels, public IDs,
  function services) and a complete file-naming table.
- **Starter code follows its own rules:** the contact form is split into
  single-responsibility components and hooks, sample models expose public UUIDs,
  and the starter enables the Oxlint rules its standards require
  (`no-explicit-any`, explicit member accessibility, `curly`, `no-console`).

## 3. Added: one JSON error shape (`core`)

`http.errorResponse` is an optional formatter for every JSON error response
(400–599), including errors Fastify produces before routing (body parsing,
unmatched routes, global rate limits):

```ts title="src/config/http.ts"
import type { HttpConfigurations } from "@warlock.js/core";

const httpConfig: HttpConfigurations = {
  errorResponse: ({ status, body, requestId }) => ({
    error: { code: String(status), message: "Request failed", details: body },
    requestId,
  }),
};

export default httpConfig;
```

It is off unless configured. HTML, file and stream responses are untouched; a
formatter that throws or returns `undefined` leaves the original response. New
apps from `create-warlock` configure it to produce `{ error: { code, message } }`.

## 4. Changed for upgrades

The `warlock upgrade` Oxlint template for apps migrating from ESLint now also
enables `typescript/no-explicit-any` and `curly`, matching new apps. Expect new
diagnostics in migrated apps that use `any` or braceless blocks.
